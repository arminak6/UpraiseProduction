# A7 - Replace a teaching chunk and regenerate its voice

Current contract: user-approved replacement behavior, 2026-10-13.

`POST /v1/audio:regenerate` edits one existing teaching chunk in the selected
difficulty level, or its corresponding chunk in every aligned level. It retains
the lesson job ID and chunk IDs. Successful processing replaces current text,
exact SSML and WAV together. Other chunks keep their content. Old teaching versions
are not retained or listed as Prepared lessons.

## Input

Production requires OAuth/mTLS and matching client/course access.
No learner session JWT is needed. Generation/TTS operator controls apply.

```json
{
  "lesson_job_id": "<existing-lesson-job-UUID>",
  "chunk_id": "<existing-chunk-UUID>",
  "teacher_review": "Explain this part more simply and remove the final question.",
  "apply_to_all_levels": false
}
```

Feedback is nonblank, at most 8000 characters. Extra fields and invalid UUIDs
are rejected. Language, voice, level and source scope are inherited. The lesson
must be DONE, accessible and undisposed with intact artifacts and
matching PostgreSQL teaching text. Structural changes require a new A3 plan.
Temporary output must be unexpired; a [saved course package](lesson-archive.md)
remains revisable after its temporary files have expired and been cleaned.

`apply_to_all_levels` is an optional strict boolean, default **false**. False or
omitted edits only the selected level. True requires an A3 v2 aligned bundle and
uses the selected chunk's shared `content_unit_id` to find its counterpart in
every available level. The same feedback is applied with each level's own
difficulty profile, current text, neighbours and inherited language/voice. A v1
or standalone single-level lesson returns 409 `REVISION_ALL_LEVELS_UNAVAILABLE`.

## Output and progress

HTTP **202**, `Location: /v1/jobs/<processing-job-id>`:

```json
{"job_id": "<processing-job-UUID>"}
```

This new ID is for processing status, not a new prepared lesson. A4 reports the
usual SOURCE/GENERATE/REVIEW/FINALIZE/TRANSLATE/SPEECH/PUBLISH/DONE steps, progress,
attempts and errors. After successful publication its result summary includes:

```json
{
  "replacement_target_job_id": "<existing-lesson-job-UUID>",
  "learner_level": "advanced",
  "apply_to_all_levels": true,
  "revised_levels": ["beginner", "intermediate", "advanced"],
  "chunk_id": "<edited-chunk-UUID>",
  "lesson_status": "DRAFT",
  "result_sha256": "<current-result-SHA-256>"
}
```

Fetch the updated lesson and voice using its **existing lesson job ID** through
A5. Reading A5 using a completed, undisposed processing ID also resolves to the
current edited level; the response's `job_id` is the existing lesson ID and
audio URLs use that ID. A8 lists the original lesson/levels, with no separate
entry for the processing job. Every result remains DRAFT for human review.
The summary also maps each revised level to its edited UUID in `chunk_ids`.
`learner_level` remains the teacher's selected level for A5 aliasing/navigation.

The final A7 review receives the teacher's feedback and original chunk. It permits
requested cosmetic edits (for example lecturer or institutional attribution),
while preserving the unit's teaching facts, mathematical meaning, language and
difficulty. If rejected, the editor receives the specific findings and gets at
most **two correction attempts**. Each new candidate is checked again. Candidate
text, its matching review and correction count are checkpointed; accepted text
and review are reused after a speech/storage outage. Exhausted review rejection
is terminal, rather than repeating the rejected candidate through job retries.

For `REVISION_ALIGNMENT_REJECTED`, A4's existing `error` object also includes
`stage`, `learner_level`, `chunk_id`, `chunk_index` (zero-based), `reason`,
`correction_rounds`, `max_correction_rounds` and `review` (three acceptance flags,
bounded `issues` and `revision_instructions`). The UI shows the affected part and
actionable findings. Detailed findings are temporary author output in checkpoints
and the failed job summary; they are excluded from audit/logs and removed by
A6/TTL/A2. Older failed jobs without retained findings still return their code.
A7's public request and HTTP202/job_id response are unchanged.

Before alignment review, invalid final-text JSON or deterministic text/citation
validation also gets at most **two final-output corrections per finalization
attempt**. Each editor call
receives the specific validation finding, teacher feedback and pinned sources;
every replacement passes the same strict JSON, text and citation checks. Invalid
JSON is regenerated, never accepted through loose string repair. This budget is
separate from alignment corrections; exhausted final-output failure is terminal.
The A4 `REVISION_MODEL_INVALID_OUTPUT` error includes safe fixed `reason` and
`reason_code`, model `stage`, affected level/chunk, and correction counts. Provider
replies and exception text are not exposed. Earlier generation/review schema
failures remain retryable under the existing job limit. Details share the same
temporary lifecycle as alignment findings. Older errors cannot be reconstructed.

## Publication, failures and concurrent edits

1. Accept an immutable temporary snapshot of the selected level or whole bundle,
   verify original sources/text/audio and record each target chunk's fingerprint.
2. Run the existing three-role generation/review/editor and checked translation
   if required. Preserve teaching-unit identities. Save temporary prepared text
   and exact SSML before TTS. Generate speech only for the targeted chunks. All-level
   requests process levels sequentially in one job, with separate reusable
   checkpoints and overall progress; each level retains its difficulty profile.
   Corrections are checked in the lesson's output language, preserving its voice.
3. Under processing ownership, source locks and the existing lesson's artifact
   lock, read its latest content. Replace only the targeted chunks; preserve
   unrelated edits made after submission. If another edit already changed the
   any target chunk, fail the whole request with `REVISION_TARGET_CHANGED`.
4. Prepare and verify a complete artifact directory before publication. One
   PostgreSQL transaction switches the lesson's artifact pointer and result
   integrity hash, updates its retained text/SSML, and completes the processing
   job. Readers use the stable lesson ID and matching current manifest.
5. Remove superseded artifact directories, request snapshots, teacher feedback,
   diagnostic checkpoints and processing-job prepared copies. Minimal IDs,
   progress and content-free audit remain. Cleanup is idempotent and recoverable;
   a cleanup outage does not undo a successfully published update.

Failure or cancellation before publication leaves the current lesson intact.
For all-level requests, no level is published until every level's text/audio
succeeds. A failure or cancellation of any level preserves all current levels.
Cancelled, received or expired unpublished A7 candidates dispose their temporary
prepared text/plans as well as artifacts; current lesson text remains retained.
Source/course deletion, receipt or expiry before publication prevents replacement
(`REVISION_TARGET_UNAVAILABLE`). Other usual errors include 404 inaccessible
resource/chunk, 410 expired output, 422 invalid input and 503 dependency/lock
errors. Worker retries reuse checkpoints; provider calls are at least once.

A successful replacement refreshes the current lesson's A5 expiry by its
configured TTL (24 hours by default). A6 on the existing lesson removes its
current temporary output but preserves retained text. A6 receipt/cleanup of a
processing job does not remove artifacts still owned by the current lesson.
A2 source/course deletion also removes current replacement artifacts and text.
With the persistent archive enabled, publication also saves the new complete
package before switching the database pointer, then removes the superseded
package. Temporary TTL cleanup does not expire that saved course.

Sessions bind the exact lesson result hash. A changed lesson closes stale RAM
sessions through the sweep or before their next B2/B4 action. Production requires
fresh human approval and a matching session assertion for the updated DRAFT.

## Existing revisions and UI

Startup consolidates available older A7 revision chains using stored artifacts,
without model/TTS calls. The latest snapshot of each level is copied into its
original available lesson; old prepared copies and snapshots are removed. If the
former original bundle already expired, an available revised level is retained as
its stable current lesson, without reviving expired sibling audio. Consolidation
is repeatable and preserves current text/voice exactly.

Both A7 UI screens show inline status/stage/percentage every five seconds. Terminal
states stop polling; HTTP errors pause it until manual refresh. Success reloads
the same lesson and edited level/chunk, clearing cached old text. **Open updated
lesson** also reloads it explicitly.
Loading an existing lesson (A5 GET/200) and submitting a revision (A7 POST/202)
have separately labeled HTTP details.
Both screens include **Apply revision to all difficulty levels**, unchecked by
default. Checked submits `apply_to_all_levels: true`; unchecked edits only the
selected level. All-level completion is identified in the progress panel.

Every explicit POST still creates a processing job; A7 request idempotency remains
deferred. The UI does not automatically retry POST or submit on navigation.
