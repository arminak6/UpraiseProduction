# A3 v2: aligned difficulty levels

`POST /v2/lesson-jobs` generates selected difficulty levels in one job, defaulting
to all configured levels when `levels` is omitted or null.
`POST /v1/lesson-jobs` retains single-level generation. Existing lessons are not
converted or changed. OAuth/mTLS, course/source ownership,
optional Idempotency-Key and callback requirements are the same as A3 v1.

## Request

```json
{
  "lesson_id": "aligned-course-test",
  "course_id": "test-course",
  "activity_id": "test-activity",
  "document_ids": ["79fd4c5e-b3ef-426e-bf47-78ae09a2ef0e"],
  "language": "en",
  "voice": "Joanna",
  "levels": ["beginner", "intermediate"],
  "options": {
    "source_window_pages": 5,
    "target_chunk_words": 200,
    "max_chunk_words": 500
  }
}
```

The optional top-level `levels` array selects 1–8 unique names from the server's
configured profiles. Empty, duplicate, malformed or unconfigured selections
return 422. Custom configured names are supported. Only selected variants receive
text and audio; selection is saved with the job and included in its idempotency
fingerprint. Selection order is normalized to server configuration order, so
reordering the same selection preserves retries. Existing callers that omit
`levels` retain all-level generation; A3 v1 is unchanged.

The planning level is the configured `UPRAISE_LESSON_PLAN_LEVEL` when selected;
otherwise it is the first selected level in configuration order. Profiles and
planning level are snapshotted per job without changing deployment settings.
The input has no `options.learner_level`. The response is
`202 {"job_id":"…"}` with the existing A4 Location. A4 reports
`levels`, `chunk_count` per level, `chunk_counts`, `total_chunk_count`, and
`chunk_plan_id`. For example, 20 units × 3 levels = 60 text/audio chunks.

## Workflow and guarantees

1. Await A1, read the active extracted source from Qdrant in document/page order.
   PDF extraction is not repeated for each level.
2. Generate canonical teaching material once per source window with the existing
   generator/reviewer/editor, in the document's declared language.
3. Segment that material once into a common ordered plan. Each unit has a stable
   `content_unit_id`, fixed source pages/chunk references, and canonical material.
4. For each level, the original generator → reviewer → editor workflow adapts
   those same units. An accepted draft is retained; otherwise the editor applies
   the draft review using the same sources. There is no additional blocking
   post-edit material-preservation review; it is deferred in FUTURE_UPDATES.md. Code
   checks exact unit IDs/order, math/text formatting and valid source page references.
   Different wording, scaffolding, length and duration are allowed. Required facts,
   formulas, topic/order and source scope must remain aligned.
   Math follows the original Uprise/v2 source-review strategy: preserve meaning,
   not the exact spelling of every delimited expression. Equivalent notation
   (`H_0` / `H_{0}`), regrouped symbols and simpler prose are allowed. Original
   math delimiter recovery runs before speech. Unusual markup
   keeps the original speech recovery path. The draft reviewer checks facts,
   values, operators, assumptions, contradictions and missing material against
   both canonical units and original sources. It does not require identical
   wording inside LaTeX text commands. Negative draft findings are supplied to
   the editor and retained in the returned DRAFT reports; editing does not imply
   independent final verification or human approval. Format, ID, citation and
   word bounds still apply to the final text. Optional
   local-development model diagnostics use the existing opt-in capture setting;
   public errors and logs never expose formulas or generated text. Authorized A5
   results include the draft review's issues and revision instructions.
   Structured responses recover complete JSON wrappers and damaged string escapes
   (such as LaTeX backslashes or literal newlines), preserving correctly encoded
   strings. Missing structure/fields, ambiguous payloads/duplicate keys and unclear
   math escapes are rejected rather than guessed. Native-response fallback asks
   explicitly for a JSON instance with all unit IDs and correct string escaping.
   Truncated responses get one retry with a doubled token budget (maximum 16000);
   persistent truncation reports `LESSON_ALIGNMENT_INCOMPLETE`. Provider errors
   retain their existing AWS/dependency classification. Invalid model responses
   retain `LESSON_ALIGNMENT_MODEL_INVALID`, with content-free stage/reason logs.
   Draft, review, editor and shortening responses also validate their exact unit
   ID sequence inside response recovery. An ID mismatch gets one
   corrective request with the required IDs/order and unit count; returned IDs
   are never reassigned or silently reordered. Persistent mismatches retain
   `LESSON_ALIGNMENT_IDS_INVALID`. Logs and RETRY/FAILED audit events include the
   stage and expected/received/missing/unexpected/duplicate counts plus an order
   mismatch flag, without model text or returned IDs. Pipeline v2.5 records
   `identity_recovery=aligned-unit-id-recovery-v1` in C5 and bundle provenance.
   Format/token fallback does not consume identity correction: at most three calls
   are allowed when both failures occur. Persistent format failures still stop
   after two calls; persistent ID mismatches receive only one correction request.
5. If the requested language differs, translate with the existing checked
   translation path, preserving paragraph/unit identities and notation.
6. Enforce the requested maximum word count. Attempt shortening without dropping
   material. If this still fails, refine the common plan and regenerate variants
   for the changed units at **every** level. At most two shared refinements are
   allowed. An indivisible oversized unit fails; no silent truncation or separate
   level-only split is allowed.
7. Commit the shared plan and every level's finalized text to PostgreSQL before
   TTS. Save exact narration SSML before synthesis. Each level has a distinct
   `chunk_id` and WAV; corresponding chunks share `content_unit_id` and index.
8. Publish one complete DRAFT bundle only after every level's speech is ready.
   Checkpoints allow retries without repeating completed work. A failed variant
   cannot be fetched as a partial bundle. AI checks are not human approval.

The 200-word target is flexible; the default 500-word maximum is enforced after
translation. Limits: target 30–1000, maximum 50–2000, target ≤ maximum. There is no
fixed course chunk count: the common plan determines it. Semantic alignment uses
AI review and still needs human assessment; count/identity/order are code-enforced.
All levels currently run sequentially within the existing lesson worker.
Generating several variants costs more provider calls than A3 v1.

## Results and downstream APIs

- `GET /v1/jobs/{job_id}/result` returns a bundle with `variants`, shared
  `chunk_plan_id`, `content_unit_ids`, per-level `chunk_count`, source-attempt
  provenance, aggregate review and versions. Every variant contains the usual
  LessonResult, its level and aligned chunks, text, SSML, audio URLs and visemes.
- `GET /v1/jobs/{job_id}/result?learner_level=beginner` returns that level in the
  familiar single-lesson shape. An unknown level returns 404. The integrity hash
  pins the complete current bundle, including the selected level. A7 changes its
  hash when replacing a chunk; sessions bound to the previous hash close. A7 can
  also replace the same shared teaching unit across every level with
  `apply_to_all_levels: true`; publication is atomic across all levels.
- Audio download keeps `GET /v1/jobs/{job_id}/audio/{chunk_id}`; chunk IDs are unique
  across levels. A8 lists each level separately, with pagination after expansion.
- B1 receives `learner_level` for a bundle. Production session JWT must bind that
  level, the job and complete result hash. B2/B4/B5 authorize the same binding;
  another level's chunk cannot be used inside the session.
- A7 identifies the level from its unique chunk ID. It replaces that chunk in the
  existing bundle, retaining the lesson ID, plan, unit IDs, count and ordering;
  other chunks and difficulty levels keep their content by default. With
  `apply_to_all_levels: true`, the same shared unit is revised in every level,
  preserving each difficulty profile and publishing together after success.
  Core material and maximum length are checked again. Structural changes need
  a new A3 plan.
- A6 receipt/cancellation and the existing 24-hour output TTL apply to the entire
  bundle and all its WAVs. Durable PostgreSQL text/SSML/plan remain retained.
- C5 includes aligned pipeline/profile fingerprints, plan version, batch size,
  default bounds and alignment prompt provenance. New audits remain content-free.

Frontend2 submits generation through A3 v2. **Preview courses** groups the
available levels into a single course and passes the selected level to B1.

## Configuration and migration

`UPRAISE_LESSON_LEVEL_PROFILES` is an ordered JSON object of trusted operator
level-name → teaching-profile text. Defaults: beginner, intermediate, advanced.
`UPRAISE_LESSON_PLAN_LEVEL=intermediate` must match a configured key.
`UPRAISE_LESSON_ALIGNMENT_BATCH_UNITS=4` batches up to eight units per model call.
One to eight named profiles are supported; names use `[a-z][a-z0-9_]{0,39}`.
Configure API and workers together, drain old jobs before changing configuration,
restart them, and use a new idempotency key. Adding profiles requires no API change.

The repeatable migration adds `level_key`/`content_unit_id` to prepared chunks,
changes uniqueness to `(job_id,level_key,chunk_index)`, and adds `lesson_chunk_plans`.
Legacy rows keep the empty level key and their existing text, indexes and audio.
No source re-ingestion, content backfill or volume reset is required.
