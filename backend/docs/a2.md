# A2 – List or remove ingested material

A2 preserves the draft's two methods and the detailed document_id placeholder.
It uses the existing OAuth/mTLS INGRESS and the approved PostgreSQL operational
registry. No extraction, embedding or other AWS call occurs in A2.

## List

`GET /v1/documents?course_id=25`

`GET /v1/documents` lists all material in the caller's authorized courses. This
optional-filter extension supports the user's 2026-10-12 request for a single
frontend button showing all ingested material; existing filtered requests remain valid.

Requires authentication and authorization for an explicitly requested course. Returns HTTP 200 with a JSON array, newest submission first. An empty course
returns `[]`; an empty course_id returns 422, and an unauthorized explicit course
returns 403. Unfiltered lists omit unauthorized courses before reading their vectors.
Only the calling Middleware client's documents are visible, matching
A4's existing client isolation. There is no implicit pagination or truncation.

```json
[
  {
    "document_id": "204fdd2b-f5b7-4d81-9e34-82288fc27de5",
    "course_id": "25",
    "activity_id": "310",
    "language": "it",
    "source_ref": "48127",
    "content_hash": "Moodle-declared-revision",
    "version": "2",
    "filename": "teaching.pdf",
    "status": "DONE",
    "progress": 1.0,
    "chunk_count": 4,
    "created_at": "2026-10-02T10:00:00Z",
    "updated_at": "2026-10-02T10:02:00Z"
  }
]
```

Statuses are `QUEUED`, `RUNNING`, `DONE`, `FAILED`, or `CANCELLED`; `progress` is
the operational job's current fraction from 0 through 1. The frontend formats it
as a percentage with two decimal places. Version is nullable and
content_hash remains unverified source metadata. Queued/failed submissions are
included so a professor can monitor all accepted material, including documents
that have no vectors yet. They have chunk_count 0. For DONE documents, Qdrant is
read using course_id, document_id and the authoritative active_attempt token;
chunk_count is the exact current vector count, not the historical job result.
If vectors are missing, the historical ingestion status remains DONE while the
current count is zero. Vector-service failures return 503, not an invented count.
Document text, embeddings, signed URLs, internal job IDs and retry tokens are
not returned. List requests produce no audit event, following A2's delete-only
audit flow.

## Delete

`DELETE /v1/documents/{document_id}`

The UUID must belong to the calling Middleware
client and one of its authorized courses. Unknown/inaccessible IDs return 404;
invalid UUIDs return 422. Deletion may target queued, running, failed or completed
ingestion. A successful response is **204 with an empty body**.

The orchestrator coordinates the existing storage adapters:

1. Lock the operational row and commit a durable deletion request. This hides
   the document from A2, makes A4 return 404, clears its publication/lease tokens
   and prevents new claims, heartbeat renewals and vector publication.
   Then fence all the caller's lesson jobs in this course whose document_ids
   include this source. This includes every difficulty, language, generation and
   A7 revision, regardless of status, A6 receipt or expired temporary output.
   Delete their PostgreSQL text/SSML and shared teaching plans; scrub revision
   feedback/canonical material from job metadata. Stop affected RAM sessions.
   Remove their temporary JSON/audio/checkpoints under the artifact lock.
   A multi-source generation is removed in full if it used the deleted document.
2. Lock the row again and delete Qdrant points by **course_id AND document_id**,
   across all attempts. Wait for application and verify an exact remaining
   count of zero. Publication uses the same row lock, so a stale worker cannot
   recreate deleted vectors.
3. Persist the minimal `DOCUMENT_DELETED` audit event, then mark deletion
   complete in the operational registry. Return 204 only after source and lesson
   cleanup have acknowledged. A busy lesson writer returns503 JOB_CLEANUP_PENDING;
   its lease/publication access is already revoked and recovery resumes cleanup.

Repeated authorized deletion of the same known ID returns 204 without duplicate
audit. Concurrent deletes serialize. If Qdrant, audit or the completion commit
fails, the response is 503 and the deletion request remains durable and hidden.
Retry the same DELETE; the ingestion worker also recovers pending deletions
between ingestion jobs. A crashed process cannot reactivate the document.
Database lock waits are bounded; a 503 while publication owns the row can be
retried. A request already accepted by A1 cannot be resurrected by reusing its
old Idempotency-Key: it returns 409 DOCUMENT_DELETED for the same submission.
An intentional re-upload needs a new key and receives a new document ID.

Deletion removes indexed course material. Operational history, audit and local
source/extraction checkpoints retain the existing retention policy; completed
deletions are eligible for configured artifact cleanup even if ingestion was
unfinished. Cleanup remains disabled by default. This is
not an audit-erasure or source-file-purge API. No Moodle file is deleted. Future
retrieval must check **no deletion request + DONE + matching active_attempt**.
PostgreSQL/Qdrant/audit commits are not a distributed atomic transaction.

## Delete an entire course

`DELETE /v1/courses/{course_id}` requires authenticated client and course
access. The client identity additionally scopes both stores; another client's
documents with the same course ID are preserved. Success returns204, empty body.
Unknown courses return 404. Denied course access returns 403. Oversized IDs return 422.

This deletes all the caller's Qdrant source material for that course and all its
saved generated lesson text/SSML, plans, revision content and temporary lesson
files across languages, levels, versions and job states. Minimal operational IDs
and content-free audit remain. Original ingestion PDFs/extraction evidence retain
their independent artifact policy; this API does not delete Moodle files.

A durable course_deletions row blocks A1/A3/A7 acceptance while cleanup is pending.
Sources are tombstoned before lesson rows are fenced, avoiding publication lock
inversion. New lesson acceptance locks/checks its sources in the acceptance
transaction. No writer can republish deleted content. Repeating DELETE resumes
partial cleanup; ingestion-worker recovery handles crashes/outages. Once complete,
new material may be ingested using fresh document IDs and retry keys. Stale recovery
cannot delete that newly ingested material. A later explicit DELETE removes it.

Qdrant material and PostgreSQL lesson text have no scheduled expiry. A5 temporary
JSON/WAV still expires24h after completion; A6 receipt/TTL preserves permanent
text unless document/course deletion was explicitly requested.

## Draft interpretation and testing

The draft describes reading vectors in Qdrant but does not define the list JSON
or visibility of unfinished submissions. The implementation combines the
already-approved operational registry for status/version with Qdrant reads for
active vector counts, rather than inferring job status from unfinished vectors.
This operational detail is recorded separately from the preserved Word inventory.
The previously unresolved `{id}` / `{document_id}` placeholder is resolved for
A2 by the user's explicit request to implement its detailed document_id path.

Frontend2 shows the caller's accessible documents and processing progress under
**Upload material**. Use the row's remove action to remove a document and its
dependent courses. See [Frontend2 setup](../../frontend2/README.md).
Actual Moodle OAuth/mTLS configuration is required for production integration.
The explicitly approved local testing mode supports A1/A2/A4 without those
credentials on this workstation; see local-testing.md.

Maintained tests use isolated real PostgreSQL schemas/Qdrant collections,
deterministic extraction/embedding doubles, and synthetic PDFs. They cover
status/version, client/course access, no-content responses, all-attempt
removal, queued/running cancellation, stale-worker fencing, interrupted deletion
recovery, retry identity and concurrent deletes. Runtime A1 uses the unchanged
old Docling/Nova/Titan pipeline.

Filter/wait semantics follow the official [Qdrant points API](https://api.qdrant.tech/api-reference/points/delete-points)
and [filtering documentation](https://qdrant.tech/documentation/search/filtering/).
