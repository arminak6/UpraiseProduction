# B1 - Lesson start

`POST /v1/sessions` opens an in-memory learner session for one exact, available
A3 lesson generation. The user approved this on 2026-10-07, keeping the existing
24-hour temporary lesson retention and one backend process. B1 performs no
generation, translation, speech synthesis or RAG search. Playback still uses A5.

## Input

JSON body:

| Field | Required | Meaning |
| --- | --- | --- |
| `course_id` | Yes | Authorized course, matching the selected generation |
| `activity_id` | Yes | Activity matching the selected generation |
| `lesson_id` | Yes | Lesson matching the selected generation |
| `lesson_job_id` | Yes | Exact A3 `job_id` selected from A8; prevents ambiguity across generations/languages/levels |
| `document_ids` | No | Nonempty unique subset of that lesson's A1 source IDs; defaults to all its sources |
| `language` | No | Must match the prepared lesson language, case insensitive; defaults to it |
| `session_id` | Local preview only | Optional UUID for retrying the same session start; otherwise generated |
| `consent_scope` | Local preview only | Unique array of `questions` and/or `telemetry`; defaults to no consent |

Unknown body fields are rejected. The explanation level and voice are taken
from the prepared lesson, alongside the language; B1 never changes a generation.
Its source documents may be in a different language from its teaching text.

## Production identity, consent and approval

Existing service OAuth/mTLS INGRESS still applies. The service access token needs
the appropriate `upraise_courses`. The additional signed
Middleware assertion is supplied in `X-UPRAISE-Session-JWT`, separate from
`Authorization: Bearer <service-access-token>`.

Configure `UPRAISE_SESSION_JWT_ISSUER`, `UPRAISE_SESSION_JWT_JWKS_URL` (HTTPS)
and `UPRAISE_SESSION_JWT_AUDIENCE` (default `upraise-learner-session`, different
from the service OAuth audience). Only RS256/ES256 are accepted. JWT signature,
issuer, audience, expiry and issued-at are checked. Required claims:

```json
{
  "iss": "https://middleware.example",
  "aud": "upraise-learner-session",
  "sub": "pseudonymous-learner-reference",
  "iat": 1791367200,
  "exp": 1791369000,
  "session_id": "<UUID chosen by Middleware>",
  "client_id": "<authenticated Middleware client ID>",
  "course_id": "test-course",
  "activity_id": "test-activity",
  "lesson_id": "italian-translated-test",
  "lesson_job_id": "<selected A3 job UUID>",
  "result_sha256": "<exact A4/A5 result SHA-256>",
  "consent_scope": ["questions"],
  "lesson_approved": true
}
```

The example timestamps are illustrative; Middleware must issue current tokens.
Middleware's trusted assertion attests its external human approval of this exact
result. The AI module continues to store/report its generated content as DRAFT;
AI review is never treated as human approval. This approval assertion mechanism
is the B1 integration contract; a real Middleware issuer still needs configuration.
A7 replaces content under the existing lesson ID. The changed result hash
invalidates older sessions/assertions; fresh approval and a matching session JWT
are required for the updated DRAFT. See [A7](a7.md).

Body session/consent claims are forbidden with a signed assertion. The session
is bound to the client, pseudonymous JWT subject, exact generation/result hash,
course/activity/lesson, source scope, language, level, consent and preview mode.
No JWT or learner subject is stored in audit or PostgreSQL session state.

## Local development preview

Only explicit `environment=development` + `local_test_mode=true` and the existing
private/loopback INGRESS permit JWT-free draft previews. Ownership and available-source checks use the fixed testing client.
No real learner approval is implied: the response has `preview=true`.
If a session JWT is supplied, it is verified; local mode never accepts an unsigned
assertion. JWT-free local body consent is solely a development simulation.

One-line PowerShell test using the existing Italian generation, while it remains available:

```powershell
curl.exe --% -i -X POST "http://localhost:8000/v1/sessions" -H "Content-Type: application/json" --data-raw "{\"course_id\":\"test-course\",\"activity_id\":\"test-activity\",\"lesson_id\":\"italian-translated-test\",\"lesson_job_id\":\"47194bc7-dc36-4a53-b635-15dad2832c3c\"}"
```

Select a current job from A8 if that generation has expired or was acknowledged.
Adding a stable `session_id` to the local body makes network retries idempotent.
Without it, each local request intentionally opens a new session.
Production requests additionally need the service bearer token, configured mTLS
gateway and the signed session assertion header.

## Output

`201 Created` for a new session; `200 OK` for an identical active session retry.
Responses use `Cache-Control: no-store`. Fields:

- `session_id`, `lesson_job_id`, `lesson_id`, `course_id`, `activity_id`;
- resolved `document_ids`, `language`, `learner_level`, `voice`, `result_sha256`;
- `preview`, `ai_notice`, `expires_at` (UTC).

The response omits `capabilities`, as approved on 2026-10-07.
B4 learner interruptions are implemented separately; see [B4](b4.md).
B2 chunk-end decisions and B5 session end are implemented; see [B2](b2.md) and
[B5](b5.md). B3/B6 and streaming remain unimplemented.
Consent is retained in RAM for later runtime APIs; it cannot enable a missing
service. Lesson text/audio and internal chat/cognitive state are not returned.
The AI notice is static in EN/IT/FR/DE/ES, with English fallback for other languages.
The consuming UI/Middleware must display it at the start of the interaction.
Frontend2 lists lessons through A8 and starts B1 when the reader opens a preview
at the selected difficulty. The form accepts a signed middleware session JWT or
local questions consent in JWT-free preview mode. The same session is used for
B4 questions and closed through B5.

## Flow and lifecycle

1. INGRESS and signed session authorization (or explicit local preview).
2. Resolve exact A3 generation: client/course access, matching context, DONE,
   nonexpired output, no cleanup request, active undeleted source documents,
   A5 result integrity and existing WAVs. Audio hashes remain checked by A5 when fetched.
3. Policy & Consent: retain permitted consent in RAM for later runtime APIs.
4. Initialize isolated RAG scope, empty chat cache, first chunk position,
   cognitive-load placeholder and zeroed Prompt Guard counters.
5. Commit content-free `session_started` audit before making the new session available.
6. Return session metadata and AI notice.

The dictionary is thread safe and bounded (`UPRAISE_SESSION_MAX_COUNT=10000`).
Unrelated learners can start concurrently; concurrent duplicate starts receive
retryable 409 until the first completes. Identical retries preserve chat/state
and never extend expiry, recheck lesson availability, and produce no duplicate
start audit. A shorter token/content deadline shortens an existing session.
Changing the binding of an active session requires a new session UUID.

`UPRAISE_SESSION_TTL_SECONDS` defaults to 1800 (30 minutes). Expiry is capped by
lesson output expiry and, for signed requests, JWT expiry. B1 retries do not extend
it. Until later runtime APIs implement activity renewal, this is a fixed start TTL.
Expired sessions are removed on access/start and by a background sweep every
`UPRAISE_SESSION_SWEEP_SECONDS` (default 30). Monotonic deadlines also prevent a
backward wall-clock adjustment from lengthening a session.

All runtime state disappears when the backend process stops/restarts. Audit
history remains; it never restores chat/sessions. Keep one backend process:
multiple processes/replicas need a future shared session store. No Redis or new
session database table is introduced. B5 explicit end clears learner state/audio
and records session_ended; automatic fixed-TTL expiry uses the same cleanup.
Starting B1 neither extends temporary A5 retention nor acknowledges A6 receipt.
Saved [persistent packages](lesson-archive.md) remain playable beyond temporary
expiry; their sessions are capped by the usual session/token deadline.
Runtime APIs must recheck authorization, consent, source activation and cleanup
when accessing stored sessions; having a RAM session cannot bypass deletion.

## Errors

| Status | Examples |
| --- | --- |
| 401 | Missing, expired, forged or malformed session assertion |
| 403 | Denied course access, assertion/client/scope mismatch, absent external approval, disallowed RAG documents |
| 404 | Generation inaccessible to the client/course; another client's session UUID |
| 409 | Generation not ready, unavailable sources, context/language/hash mismatch, active session rebinding, concurrent duplicate start |
| 410 | Lesson output expired/acknowledged, or session expired while opening |
| 422 | Invalid JSON fields, duplicate/empty scopes, production body session/consent claims |
| 503 | Unconfigured storage/session identity, unavailable identity/audit storage, missing/corrupt artifacts, busy cleanup, full session capacity |

An audit failure leaves no available session. Error bodies never expose tokens,
provider errors or private database messages. B1 can be retried after recovery.
